Autonomous engineering

How a team of agents writes software

A developer gives the teams their goals and the rules for their work. Each team has a coordinator. The agents can continue work on different goals while the developer examines one design.

Greg Lapinski · November 2026

How a goal becomes a task

The developer usually gives a goal to the Assistant. The Assistant sends it to the coordinator for that project. The coordinator divides the work into tasks and selects a coder for each task. If the work involves two projects, the coordinators speak directly to each other.

Each team has coders and an integrator. Reviewers and an evaluator join for one task. If a proposal needs another opinion, the Consultant can examine it independently.

When a coordinator has a result or needs a decision, the Assistant takes the report or question back to the developer. The developer can also speak directly to the agent responsible for a task. The other teams can continue their work during that discussion.

The same rules for each goal

The team has written rules for design, changes to code, tests, communication and operations. The rules tell each agent what to do and what to record. The next agent uses this record to continue the task.

How the work continues between sessions

An agent can stop before the team completes a goal. Engram keeps the task records. Each record identifies the agent responsible for the task. The record also contains decisions and questions that still have no answer. A new agent can read the record and continue the task.

TermAl runs the agent sessions and sends messages between them. The Engram team and the TermAl team use these two tools. Each team has a coordinator, coders and an integrator. For a change to the two projects, the coordinators can send messages directly to each other.

Data, permissions and models
Data that goes between computers
The computers send messages, test requests, Git commits and test results to each other. Installation of the synchronization function continues. This function sends task descriptions and project memory between computers.
Data and permissions on each computer
Task claims and permissions to do, review or integrate work stay on the local computer. Git worktrees, build files and temporary files also stay on that computer.

The team uses models from OpenAI, Anthropic and Moonshot. For each commit, the two reviewers use models from different suppliers. Smaller models do builds and tests.

How the team changed its process

The developer wanted to know if each change did what the team agreed to do. The team added independent evaluation to its tools. For each task, an evaluator examined the evidence. This evaluator did not write the code for that task.

With the first design, the agents sometimes could not continue their tasks. The developer stopped the evaluation process. The team found the cause and changed the design. After tests on the installed software gave the correct results, the developer started the evaluation process again.

Tests of the evaluation process

Before the system could record the completion of a task, the evaluator had to record its decision. The evaluator used the record of operations from the host computer. The decision identified the commit that the evaluator examined.

In the first test, the system accepted the decision for that commit. In the second test, the source code changed. The system did not accept the previous decision for the new commit.

The developer started evaluation again in the two projects 54 days after the team made the first version.

How the team corrected a slow interface

In one week, the teams had four goals. These included independent evaluation and a faster interface. The other goals were to send prompts to remote agents and to synchronize task records.

The developer told the team about a delay after keyboard input or a change of tab. The agents found that the interface kept a row for each session on the page. They used a component from the same project to show only the rows that the developer could see. The developer could examine the change with these agents while the other agents continued their tasks.

Test results and repository measurements

For the interface test, the team used a session list four times the size of the list in production. Before the change, the page contained 142,000 elements. After the change, it contained less than 1,000 elements.

The team also did a synthetic test on the data structure for file notifications. The new structure used 82% less memory than the old structure. The team measured only the memory for that structure.

In November 2026, the TermAl, Engram and Phoenix repositories contained 1.57 million lines of source code and test code. This total includes code from individual agents and from teams of agents.

Decisions that stay with the developer

The developer stays on the loop and can change the order of the goals. If a design has a problem, the developer can examine it with one team. The agents on the other goals continue their tasks.
