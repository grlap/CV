Autonomous engineering

How an agent team builds software

A person chooses what to build and sets the standards for the work. The agents plan, implement and check changes. Several goals can move forward at once, even while the person spends time on a single design.

Greg Lapinski · November 2026

Who decides what happens next?

In a conversation with a single coding agent, the person usually supplies the next task. Give a team a goal, and its coordinator can decide what to tackle first, who should take it and what follows when it is done. The person can still change the priority or question a design at any point.

That is what it means to have a human on the loop. A coordinator brings back a result, a blocker or a question that needs judgment. If one design needs a long discussion, the agents working on other goals can carry on.

One rulebook for every goal

The team can organize its own work because the way it works is written down. Design, coding, testing, communication and operations each have rules. When an agent picks up a task, it knows what it owns, what to record for the next agent, and how to show that the work is complete.

The loop below follows one change. The coder proposes a version. Other agents inspect the code, test its behavior and judge whether it meets the original request.

How work continues across sessions

A goal can outlast the session that started it. Engram records who owns each task, what the team has decided and which questions are open. TermAl runs the sessions and carries their messages. A new agent can read the record and pick up where the last one left off.

The teams building these two tools also use them. Each project has its own coordinator, coders and integrator. The coordinators can talk directly when a change in one project affects the other.

Team map and machine boundaries

The team draws on models from OpenAI, Anthropic and Moonshot. Two reviewers from different vendors inspect each candidate, and lighter models run builds and tests.

When the process needs to change

The team also uses this approach to improve its own tools. One example was independent evaluation. The person wanted a way to tell whether a completed task had delivered what was asked. The agents had to work out how to make that judgment reliable.

The first design sometimes prevented the agents from working. The person switched evaluation off. The team traced the problem, rebuilt the check and demonstrated that it worked on installed versions before the person switched it back on.

How the team tested independent evaluation

A task needed an explicit verdict before it could count as complete. To make that verdict trustworthy, the rebuilt evaluator used the host’s record of what had run and tied its judgment to the source it examined.

The team tested both outcomes. The system accepted an evaluation of the checked source. When the source changed, the earlier verdict could no longer authorize completion. From the first implementation to re-enabling evaluation in both projects took 54 days.

The work in practice

During one week the teams pursued acceptance evaluation, interface performance, remote prompt delivery and task-record sync in parallel. The interface work began with a simple observation from the person using it. Switching tabs and typing felt slow.

The agents traced the lag to the session list, which kept every row on the page. They found a component already in the codebase that could render just the visible rows. The person could discuss the fix with that team while work continued on the other goals.

Performance measurements and repository figures

In a controlled interface test at four times production size, the page went from 142,000 elements to under a thousand. In a separate memory investigation, the team measured an 82% reduction in a synthetic test of its file-notification structure. That test measured only the structure itself.

TermAl, Engram and Phoenix together held 1.57 million lines of source and tests in the November snapshot. These totals include the earlier stages of development, from prompting individual agents to coordinating teams.

Where human judgment matters

The person has time to ask whether a proposed design is getting too complicated, change what comes first, or follow a difficult problem all the way through. The rest of the team can keep building while that decision takes shape.
