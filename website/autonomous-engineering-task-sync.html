When two hosts agree on a task

An agent picks up a task on one computer while another agent edits its instructions on a second machine. By morning there are two versions. Which instructions should the next agent follow?

Each computer keeps a local task record in Engram, the factory’s work log. Agents exchange records through Git. An export writes local decisions to files. An import reads another computer’s changes back into the work log.

Greg Lapinski · November 2026

Both agents had work worth keeping

Imagine the task is to test a database restore. Agent A adds a check for missing files. On a second machine, agent B changes which backup to restore. Both edit the same task instructions. A commits its edit and sends it. B still has an edit in its local work log.

The agent can set the local work aside and merge the two edits explicitly. The working rule is to export and commit local planning before integrating incoming changes. That gives each decision a version the agents can recover.

Can a retry report an old error?

The team described the exchange in TLA+, a language for specifying the steps a system can take. TLC, the model checker, tried different orders of edits, commits, crashes and retries. One check asked whether each import that encounters a conflicting edit names the task it refuses to overwrite.

Here is the consequence in the model’s ExplicitConflict rule. Read h as the machine doing the import. A prime means the value after the step.

=> /\ result'[h].kind = "conflict"
   /\ {t \in Tasks : Diverges(h, t)} \subseteq result'[h].tasks
   /\ db'[h] = db[h] /\ baseline'[h] = baseline[h] /\ head'[h] = head[h]]_vars

Read the three lines in order. The new result must say “conflict.” Its list must include every task with a conflicting edit. The local task store, its comparison point and its sync record must all keep their previous values.

An early model remembered the last error. That left a hole in the check. If the first import reported a conflict and the second failed silently, the old error could make both attempts look correct.

  1. First attempt. B refuses the import and reports the conflicting task.
  2. Retry. The revised model clears the previous result when a new import starts.
  3. Deliberate fault. A test version silently refuses the second import. TLC now catches the missing report even though all the task data survives.

This change fixed a blind spot in the specification. The deliberately faulty model let the team test whether its check could tell the two attempts apart.

When the two stores converged

After the last edit, both hosts reached the same commit and task content in the two convergence checks. The order of work mattered. Each agent waited for a successful export, then committed local changes before integrating remote work. It made no new planning edit between a merge and its import. The first publisher also confirmed its first export before integrating later commits.

EventuallyConverged == <>[]Converged

Read <>[] as “eventually, and from then on.” The check asks whether, after edits stop, every copy can reach the same committed work and stay there, with no changes left to send.

These checks assumed that every continuously available sync or Git action eventually ran. They covered two hosts, one task, up to two local edits and six commits. The ordinary run allowed one crash outside the brief interval when an export replaces its recovery record. The first-exchange run allowed none. Both excluded failed database commits, external file edits and claims. The study found no new data-loss defect under these assumptions. Agreement outside the checked bounds remains an open question.

Model setup, corrections and coverage limits

TLC ran 25 configurations on version 11. The ordinary convergence run explored 163,223 distinct states. The first-exchange run explored 289,959. Other runs deliberately triggered known failures or reached a particular step, such as a retry after the database had committed an import.

The model represents task files as tokens and database transactions as atomic steps. One safety check combined two tasks, one claim and one crash. It covered the release of a held change. Convergence after a release remains untested. The model also excludes memory exchange, notes, task removal and complete imports with a saved comparison basis.

Two early failures exposed errors in the model. It first overlooked work due for export before the first commit. It also counted an import that changed nothing against the operation limit. The team corrected both errors before the final runs.

Other handoffs checked in the study

Interrupted export. A host can keep all its planning edits and lose the record that confirms a completed export. Recovery can require rebuilding that record. If the interruption leaves files on disk before the export reports success, committing them too soon can leave the next import stuck.

First exchange. A host making its first export must confirm its own commit before it takes later changes. Otherwise it can need the first export again as an explicit point of comparison.

Two writers in one folder. A separate run allowed a second writer to edit a file during an export. Its edit could be overwritten. The ordinary procedure gives one writer control of the folder for the operation.

Task identity and ownership. A new task kept the same local record after a retry. A deliberate one-for-one replacement defeated a record count but failed the identity check. An active claim held back incoming work until release. Dry runs left durable records unchanged in the configurations that checked them.

What a separate review of the code found

In one import path, the number of Git processes grows with the number of changed files and the history the importer examines. A second finding concerns recovery advice. When a Git query fails, the importer can suggest restoring the branch even though it has not established a history mismatch. Reviewers found both issues by reading the code.
