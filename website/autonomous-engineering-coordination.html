The review that could wait forever

Two agents finished a code review. The scheduler freed their slot. The agent that requested the review went to sleep waiting for a decision. Nobody had sent the question to the agent assigned to answer it.

Greg Lapinski · November 2026

Who was supposed to act next?

In this software factory, an agent can end its turn while other agents check its work. TermAl runs their sessions. Engram keeps the task record so the work can continue across turns. The agent that requests a review is the review lead. In the model, TermAl wakes the lead when both reviewers and the evaluator finish. That wake tells the lead to collect their results.

In one review, the reviewers raised a question outside the lead’s authority. The lead recorded who could decide it and told the scheduler that the review was over. The scheduler freed the slot for the next job.

At that point the lead is waiting for a reply. The person or agent with authority to decide has an empty inbox. Every message that anyone sent can arrive, and the job can still sit there all night.

How to put a missed conversation into TLA+

The TLA+ model records which messages exist, which agents are awake and what each agent is waiting for. TLC explores the orders in which the agents and the host can act. These three lines give each message a sender, a recipient, a purpose and a review round.

ENDP(r) == <<"P", "S", "END", r>>
FIND(r) == <<"P", "D", "FINDING", r>>
RUL(r) == <<"D", "P", "RULING", r>>

P is the review lead (the parent of the review sessions), S the scheduler and D the decision owner. Follow the recipients. Sending END tells S it can schedule more work. Only FINDING tells D what needs a ruling.

RulingReachesParent == (pP = "waitRuling") ~> (pP = "start")

Read ~> as “eventually leads to.” Every time the lead enters waitRuling, it must eventually reach the start of the next round. The team replayed the procedure from the stalled review in a model with two rounds, no crashes and no lost notifications. TLC found a counterexample.

  1. The lead sends END. It starts waiting for a ruling. Its mailbox record shows no outgoing finding.
  2. The scheduler reads END. It frees the review slot. The lead ends its turn. The decision owner has received nothing.
  3. Another job uses the slot. That job runs and finishes. The first review still has no agent preparing a reply.

The change to the rulebook

The implementing agent fixes an undisputed issue within its scope immediately. If an open finding of medium severity or higher needs a decision, falls outside that scope or is disputed, the lead sends it directly to the decision owner. The lead records which reply it needs, for which round, and who must wake it.

In the corrected trace the owner reads the finding and sends a ruling back. The lead reads that ruling and starts round two. The scheduler can give the released slot to the next named waiter while the decision is pending.

Which mailbox did the wake open?

The first failure needed no lost messages. A second case exposed an error in the model itself. An early version gave each agent one inbox. TermAl keeps a separate mailbox for each pair of participants. A notification identifies just one of those mailboxes.

In this trace, the scheduler wakes, reads the worker’s request and grants it. The lead’s earlier request stays in the closed mailbox. Even after the worker finishes, the scheduler can go back to sleep with the lead still waiting.

CanRead(k) == mst[k] \in Unread /\ awake[To(k)] /\ Pair(k) \in opened[To(k)]

Read the three conditions from left to right. The message must be unread. Its recipient must be awake. The mailbox shared with its sender must be open. A send receipt confirms storage. An acknowledgement records a separate step after reading. Evidence that the job ran comes from its result.

A second trace shows how recovery can work. An awake coordinator sends the scheduler a new message that names the original mailbox and request. The scheduler follows that reference, reads the original request once and grants the slot. If nobody wakes the coordinator, the model marks the wait as stalled. That mark records the failure for analysis. It does not wake a sleeping agent.

What survives a retry or a crash?

On a retry the lead recovers the existing review sessions and their results. Starting new reviewers would repeat work on the same version. If a worker crashes after producing a result, an awake coordinator can hand the run to a named replacement. Once woken, the replacement takes sole ownership, recovers the result and tells the scheduler to release the slot.

A crash also closes the agent’s open mailboxes. In version 9, when the review lead reads a recovery message, it also opens the mailbox of the agent named in its recorded wait. This makes an unread slot grant in that mailbox visible again. Before ending a turn voluntarily, an agent must read the messages in its open mailboxes and acknowledge those it read.

Who requests the evaluation after the last check?

In a separate incident, a worker finished its last required check, wrote “next turn” and went to sleep. For hours, nobody requested an independent evaluation. No event had been arranged to start that next turn.

The original model started the evaluator too early to expose this gap. An extension gave the worker a new state between the last check and the request for evaluation. TLC could now replay the mistake in eleven states. At the last step the worker was asleep, still owed a request and had named nobody to wake it.

The extension checks two ways out. The host can wake the worker when the last check settles. Or the worker can send READY to its coordinator, who wakes it in reply. In both traces the worker uses the existing test result to request the evaluation. The trace ends at that request.

How far did the checks go?

The final coordination model covered up to two review rounds, one shared slot and one worker competing with the review lead for it. With reliable delivery and the assumption that agents eventually take steps that stay available, the corrected handoffs made progress. With one lost wake or one crash, TLC checked a narrower promise. A wait must eventually end or have an explicit reason for the stall.

Bounded results and the unfinished two-fault check
  • Safety. TLC checked 81,917,317 distinct states. All safety checks held, including one owner per run and release of the slot before the next launch.
  • Progress. With reliable delivery, all six progress properties held across 965,984 states. The check for an explicit stall passed with one lost wake (10,624,032 states) and, separately, with one crash (15,126,615 states).
  • One lost wake plus one crash. The run that allowed both faults in either round timed out. With both faults restricted to round two, TLC finished exploring 50,607,200 states and all safety checks held. Time ran out during the final check for an explicit stall. That question remains open.
  • Evaluation request. The separate extension passed with a coordinator wake (49,027 states) and with a host wake (19,849 states). It covered one round with no medium-severity finding, crash or lost wake. Its three new messages omit per-pair mailboxes and acknowledgements. The evaluation itself is outside the model.
